# Вимоги та сценарії якості

## 1. Умова варіанта

Інтернет-магазин електроніки з каталогом, кошиком, оплатою, складським обліком і доставкою. Під час розпродажів навантаження зростає в рази. Ключові показники варіанта:

- піково 500 замовлень на хвилину, у 10 разів вище за середнє;
- оформлення замовлення: p95 ≤ 800 мс на стороні системи (без платіжного шлюзу);
- подвійне списання коштів неприпустиме (операції ідемпотентні);
- не допускається продаж товару, якого немає на складі;
- відмова платіжного шлюзу не має зупиняти перегляд каталогу й наповнення кошика.

## 2. Функціональні вимоги (користувацькі історії)

### US-1. Каталог і пошук

Як покупець, я хочу переглядати каталог і шукати товари за назвою або артикулом, щоб обрати потрібну електроніку.

Критерії приймання:

- картка товару містить артикул, назву, ціну та ознаку наявності;
- пошук працює за назвою й артикулом;
- каталог доступний для читання навіть тоді, коли платежі не проходять.

### US-2. Кошик і розрахунок суми

Як покупець, я хочу додавати й прибирати товари в кошику та бачити підсумкову суму зі знижкою й ПДВ, щоб знати остаточну ціну до оформлення.

Критерії приймання:

- додавання одного артикулу повторно збільшує кількість, а не створює дубль;
- ціна фіксується в позиції замовлення на момент додавання;
- знижка та ПДВ застосовуються як окремі незалежні кроки;
- підсумок не може бути від'ємним.

### US-3. Оформлення замовлення

Як покупець, я хочу оформити замовлення, обравши спосіб доставки й оплати, щоб завершити покупку.

Критерії приймання:

- порожній кошик оформити неможливо;
- доступні способи доставки: кур'єр, самовивіз, експрес;
- доступні способи оплати: картка, банківський переказ;
- під час оформлення товар резервується на складі;
- якщо товару недостатньо, замовлення лишається чернеткою, а помилка повертається як значення.

### US-4. Оплата через зовнішній шлюз

Як покупець, я хочу оплатити замовлення через зовнішній платіжний шлюз і отримати підтвердження, щоб замовлення перейшло в оплачений стан.

Критерії приймання:

- оплатити можна лише оформлене замовлення;
- запит до шлюзу містить суму, валюту, токен і idempotency key;
- успіх переводить замовлення в Paid і зберігає transaction_id;
- відмова або тайм-аут лишає замовлення в Placed;
- повторний виклик не списує кошти вдруге.

### US-5. Статус, скасування й трекінг

Як агент підтримки, я хочу бачити стан замовлення та скасовувати неоплачене замовлення до відправлення, щоб допомогти покупцеві.

Критерії приймання:

- стан видно як одне з п'яти значень: Draft, Placed, Paid, Shipped, Cancelled;
- скасувати можна Draft або Placed;
- скасування Placed звільняє резерв на складі;
- Paid і Shipped скасувати не можна: потрібне повернення коштів, яке в ЛР1 не моделюється;
- після відправлення зберігається номер трекінгу.

## 4. Сценарії якості

### QS-1. Продуктивність

| Частина | Значення |
|---|---|
| Джерело | Покупець |
| Стимул | Оформлює замовлення в піковий період |
| Артефакт | `OrderService`: перевірка кошика, ціноутворення, резервування, збереження замовлення |
| Середовище | Пік 500 замовлень/хв (≈ 8,3/с), у 10 разів вище за середнє; каталог читається паралельно |
| Реакція | Замовлення переходить у `Placed`, залишок зарезервовано, відповідь повернено покупцю |
| Міра відповіді | p95 серверної частини ≤ 800 мс без зовнішнього шлюзу; частка помилок ≤ 0,1% |

### QS-2. Доступність і ізоляція збоїв

| Частина | Значення |
|---|---|
| Джерело | Платіжний шлюз |
| Стимул | Не відповідає 30 секунд (тайм-аут або 5xx) |
| Артефакт | Оформлення замовлення й каталог/кошик |
| Середовище | Пікове навантаження |
| Реакція | Замовлення лишається `Placed`, покупець бачить помилку; каталог і кошик доступні; повтор із тим самим idempotency key не списує кошти вдруге |
| Міра відповіді | p95 каталогу ≤ 300 мс під час збою; 100% невдалих платежів не переводять замовлення в `Paid`; 0 подвійних списань на 100 повторів; частка помилок каталогу ≤ 0,1% |

### QS-3. Узгодженість даних

| Частина | Значення |
|---|---|
| Джерело | 50 покупців одночасно |
| Стимул | Намагаються купити останню одиницю одного артикулу |
| Артефакт | Склад і замовлення |
| Середовище | Пікове навантаження |
| Реакція | Рівно одне замовлення резервує одиницю; решта отримує `InsufficientStock`; залишок не стає від'ємним |
| Міра відповіді | 1 успіх із 50; 0 перепродажів; 0 від'ємних залишків; p95 ≤ 800 мс |

## 5. Ранжування сценаріїв

| Сценарій | Бізнес-важливість | Технічний ризик | Архітектурно значущий |
|---|---|---|---|
| QS-1 Продуктивність | H | H | так |
| QS-2 Доступність і ізоляція збоїв | H | H | так |
| QS-3 Узгодженість | H | H | так |

Усі три сценарії архітектурно значущі, бо кожен змінює структуру системи:

- QS-1 і QS-3 вимагають оформлення замовлення й резервування в одній транзакції без мережевих стрибків — це аргумент на користь модульного моноліту;
- QS-2 вимагає ізолювати платіжний шлюз за портом і адаптером, не включати його затримку в p95 оформлення та передавати стабільний idempotency key;
- QS-3 вимагає окремих агрегатів `Order` і `StockItem` та атомарної операції «перевірити й зарезервувати».

## 6. Трасування рішень

| Рішення | Сценарії / вимоги |
|---|---|
| Модульний моноліт, одна транзакція на замовлення й резерв | QS-1, QS-3 |
| Порт `PaymentGateway` + адаптер + idempotency key | QS-2, US-4 |
| Агрегати `Order` і `StockItem`, операції reserve/release | QS-3, US-3, US-5 |
| Фабрики способів доставки й оплати | US-3, змінюваність |
| Декоратори знижки та ПДВ | US-2 |
| `Result` і стани як окремі типи | QS-3, US-3–US-5 |
| C4-контейнери: Web, Shop Application, PostgreSQL | QS-1, QS-2 |
