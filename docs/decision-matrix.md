# Зважені матриці рішень

Оцінки 1–5 — це судження автора роботи, а не вимірювання. На захисті кожна оцінка пояснюється. Ваги виведені з сценаріїв якості та організаційних обмежень: що сильніше сценарій впливає на архітектуру, то більша вага.

## 1. Архітектурний стиль

Кандидати: **A. Модульний моноліт** і **B. Мікросервіси**. Serverless і подієвий стиль не порівнюються, бо завдання вимагає саме ці два стилі.

| Критерій | Вага | A. Модульний моноліт | B. Мікросервіси |
|---|---:|---|---|
| QS-1 Продуктивність оформлення | 5 | 5 · оформлення, ціноутворення й резервування в одному процесі, без мережевих стрибків | 3 · щонайменше один мережевий виклик «замовлення → склад» у гарячому шляху |
| QS-2 Доступність та ізоляція збоїв | 5 | 3 · репліки й БД допомагають, але падіння одного модуля зупиняє весь застосунок; деплой впливає на всі модулі | 5 · збій платежів не зупиняє каталог; сервіси розгортаються незалежно |
| QS-3 Узгодженість і відсутність перепродажу | 5 | 5 · одна ACID-транзакція на замовлення й резерв | 2 · потрібна saga/компенсація, eventual consistency і складне блокування залишків |
| Змінюваність способів доставки й оплати | 3 | 3 · новий модуль або фабрика + повторний деплой усього застосунку | 4 · можна розгорнути лише сервіс оплати або замовлень |
| Вартість розробки (1 розробник, 12 тижнів) | 4 | 5 · одна кодова база, один CI, один деплой | 2 · кілька сервісів, контракти, спостережуваність і CI/CD на одну людину |
| Складність експлуатації | 3 | 5 · один застосунок і одна БД | 2 · багато процесів, мережеві політики, розподілені трасування й інциденти |
| **Зважена сума (макс. 125)** | **25** | **109** | **76** |

Висновок: для пікових 500 замовлень/хв, жорсткої узгодженості залишків і команди з одного розробника модульний моноліт виграє з великим відривом. Головний аргумент — не продуктивність, а одна транзакція «замовлення + резерв» і відсутність розподіленої експлуатації.

### Перевірка стійкості

| Сценарій перевірки | Моноліт | Мікросервіси | Висновок |
|---|---:|---:|---|
| Ваги доступності й змінюваності = 5, решта = 1 | 50 | 54 | Мікросервіси виграють, якщо ізоляція збоїв і незалежний деплой стають головними |
| Ваги узгодженості й вартості розробки = 5, решта = 2 | 82 | 48 | Моноліт виграє, коли критичні ACID і мала команда |
| Поточні ваги | 109 | 76 | Моноліт |

Рішення стабільне для поточного масштабу. Воно переглядається, якщо з'являться кілька незалежних команд, вимога розгортати платежі окремо або навантаження зросте настільки, що окреме масштабування модулів стане економічно вигідним.

## 2. Мова й рантайм

Кандидати: **Python 3.13** і **Java 21**. Обидві мови підтримують незмінні записи, sealed-подібні ієрархії та pattern matching; різниця — у тому, хто перевіряє вичерпність: компілятор Java чи `mypy --strict` для Python.

| Критерій | Вага | Python 3.13 | Java 21 |
|---|---:|---|---|
| Виразність моделі домену | 5 | 5 · `frozen dataclass`, `Union`, `match`, короткий код | 5 · `record`, `sealed interface`, `switch` |
| Гарантії компілятора (вичерпність, незмінність) | 4 | 4 · `mypy --strict` + `assert_never`; перевірка зовнішня, не в рантаймі | 5 · `javac` сам відхиляє неповний `switch` і зміну `record` |
| Продуктивність і конкурентність на 8,3 замовлення/с | 2 | 3 · GIL не критичний для I/O, але CPU-обробка повільніша | 5 · JVM, віртуальні потоки, передбачувана продуктивність |
| Екосистема (HTTP, PostgreSQL, платіжні SDK) | 3 | 5 · багато бібліотек і швидкий старт | 4 · зрілі корпоративні бібліотеки, більше церемоній |
| Досвід розробника | 5 | 5 · основна мова автора; середовище вже готове | 3 · JDK 21 треба встановлювати, більше конфігурації |
| Простота збірки й інструментів | 4 | 5 · `pip`, `pytest`, `mypy`; одна команда `check.py` | 3 · Gradle wrapper, JDK 21, більше часу на CI |
| Споживання пам'яті | 1 | 2 · більший відбиток інтерпретатора | 4 · JVM ефективніша на довгій дистанції |
| **Зважена сума (макс. 120)** | **24** | **109** | **98** |

Висновок: Python виграє завдяки досвіду розробника, простоті збірки й достатній продуктивності для 8,3 замовлення/с. Java має сильніші компіляторні гарантії, але для цього масштабу й команди це не переважує вартості налаштування.

### Перевірка стійкості

| Сценарій перевірки | Python | Java | Висновок |
|---|---:|---:|---|
| Вага продуктивності = 5, досвіду = 2 | 103 | 104 | Java виграє на межі, якщо навантаження зросте приблизно в 10 разів |
| Вага гарантій компілятора = 5, досвіду = 3 | 103 | 97 | Python лишається попереду |
| Вага продуктивності = 5, досвіду = 0, інструментів = 3 | 88 | 95 | Java виграє; вибір тримається на досвіді та простоті інструментів |

Рішення переглядається, якщо навантаження зросте до ≈ 5 000 замовлень/хв або команда буде Java-центричною.
