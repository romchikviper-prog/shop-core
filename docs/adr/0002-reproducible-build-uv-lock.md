# ADR-002. Відтворювана збірка Python-пакета з uv lock

Статус: прийнято
Дата: 2026-11-27

## Контекст

ЛР1–ЛР4 використовували `requirements-dev.txt` із точними версіями, але без повного графа транзитивних залежностей. Для ЛР5 потрібна збірка, яка на іншій машині й у CI дає той самий результат, один артефакт із версією, за якою можна знайти коміт, і одна команда для людини та конвеєра. Python не компілює бінарник, тому «версія в бінарнику» означає версію в артефакті й у відповіді `/healthz`.

## Рішення

Джерело залежностей — `pyproject.toml`, повний граф фіксує **`uv.lock`** (43 пакети, включно з транзитивними). Розробницькі залежності винесено в `[dependency-groups] dev`; інсталяція в CI і локально — `uv sync --frozen --group dev`.

`Makefile` дає єдині точки входу:

- `make build` — генерує `src/shop/_build_info.py` з `git rev-parse --short=7 HEAD` і збирає wheel у `dist/`;
- `make test`, `make lint`, `make coverage`, `make complexity`, `make manifests`, `make image`, `make scan`;
- `make ci` — та сама послідовність воріт, що й конвеєр (без deploy).

Хеш коміту записується в модуль `shop._build_info`, який потрапляє і в wheel, і в образ. `shop.api.version` читає його через `import_module`; якщо файлу немає (локальний запуск без збирання), версія чесно дорівнює `dev`. У контейнері `/healthz` повертає `0.1.0+<sha>`.

## Розглянуті альтернативи

- **pip-tools (`requirements.txt` + `requirements-dev.txt`)** — звичний інструмент і працює на Python 3.12, але потребує окремих кроків компіляції, а `uv` уже був у WSL після ЛР4 і швидше ставить залежності. Відхилено, щоб не тримати два джерела правди.
- **Poetry** — зручний lock, але додає власний формат і ще один інструмент; для одного пакета без публікації це надлишково.
- **`pip freeze` без lock** — не відтворює граф транзитивних залежностей і не перевіряє, що lock відповідає `pyproject.toml`. Відхилено.
- **Версія лише в тегу образу, без файлу в пакеті** — `/healthz` не зміг би показати версію, а артефакт wheel не мав би сліду коміту. Відхилено.

## Наслідки

Що покращується:

- `uv sync --frozen` падає, якщо `pyproject.toml` і `uv.lock` розійшлися; CI не збере «щось інше»;
- один wheel і один образ мають однаковий `GIT_SHA`, тому за версією з `/healthz` можна знайти коміт;
- кеш uv у CI прив'язаний до `uv.lock`, тому повторні запуски швидші;
- локальна команда `make ci` повторює ворота CI, а не «схожі» перевірки.

Що погіршується:

- з'явилася залежність від `uv` і `make`; на Windows вони запускаються через WSL, бо там уже є Docker і kind;
- будь-яка зміна залежностей потребує явного `uv lock`, інакше `--frozen` зупинить збірку;
- wheel версії `0.1.0` не кодує SemVer-сумісність; для навчального проєкту достатньо локальної версії `0.1.0+sha`.

## Ризики та що перевірити

- Локальний `make build` генерує `src/shop/_build_info.py`, який ігнорується git; якщо його випадково закомітити, версія «застрягне». Файл додано в `.gitignore`.
- `uv.lock` може містити платформні wheel-и; CI на Linux і локальний запуск у WSL використовують ту саму платформу. Для macOS/ARM потрібен повторний `uv lock` або перевірка в CI-матриці.
- `make` на Windows без WSL не працює; це задокументовано в README, а CI використовує Linux-раннер.
