# ADR-004. CI/CD з воротами якості в GitHub Actions

Статус: прийнято
Дата: 2026-11-27

## Контекст

Потрібен конвеєр, який на кожен pull request перевіряє лінтер, тести, покриття, складність, маніфести й безпеку, а на `main` ще й розгортає образ у kind і робить smoke-тест. Ворота мають реально зупиняти погану зміну, а не бути декорацією. Токен CI повинен мати мінімальні права; секретів у репозиторії та логах бути не повинно. Бюджет — безкоштовні хвилини GitHub Actions, тому без хмарного кластера й платного реєстру.

## Рішення

Один workflow `.github/workflows/ci.yml` з трьома jobs:

1. **`quality`** — `actions/checkout`, `astral-sh/setup-uv` із кешем за `uv.lock`, `uv sync --frozen --group dev`, далі `make lint`, `make coverage`, `make complexity`, `make manifests` (kustomize + kubeconform + hadolint).
2. **`image`** — `docker/build-push-action` з тегом `shop-core:<github.sha>`, кеш `type=gha`; `trivy image --severity CRITICAL --exit-code 1 --ignore-unfixed`; образ зберігається як артефакт на 1 день.
3. **`deploy`** — лише `push` у `main`: kind, `kind load docker-image`, `kustomize build overlays/prod | sed` із тегом коміту, `kubectl rollout status`, `port-forward` і smoke-тест `/healthz` та `POST /evaluate` з перевіркою `total=960.00`.

Права workflow — **лише `contents: read`**; секрети не використовуються. Образ не пушиться в реєстр (для kind достатньо `kind load`), тому немає потреби в `packages: write`. Кешуються залежності uv і шари Docker; тег образу — повний хеш коміту.

Ворота:

| Ворота | Поріг | Де |
|---|---|---|
| Лінтер і формат | 0 зауважень | `make lint` |
| Тести | 100 % зелених | `make coverage` |
| Покриття рядків | ≥ 80 % (факт 84 %) | `coverage report`, `fail_under` |
| Цикломатична складність | ≤ 10 (факт 7) | `scripts/check_complexity.py` |
| Маніфести й Dockerfile | 0 помилок | `kustomize` + `kubeconform` + `hadolint` |
| Безпека | 0 CRITICAL | `trivy image` |

## Розглянуті альтернативи

- **Один job на все** — простіше, але повільний зворотний зв'язок і немає природної межі «образ не збираємо, поки не пройшли тести». Відхилено.
- **GitLab CI** — функціонально достатній, але акаунт і репозиторій уже на GitHub; безкоштовні хвилини там доступні.
- **Публікація в GitHub Container Registry** — реалістичніше для продакшну, але для локального kind зайвий крок і додаткові права токена. Відхилено; переглянути, якщо з'явиться віддалений кластер.
- **Helm** — потужніший для багатьох сервісів, але для одного сервісу Kustomize дає базу й дві накладки без шаблонізації. Відхилено.

## Наслідки

Що покращується:

- погана зміна не доходить до образу й кластера: `image` і `deploy` залежать від `quality`;
- той самий `make ci` можна запустити локально, тому розбіжність «у мене працює» менша;
- кеш uv і Docker скорочує повторні запуски;
- мінімальні права токена зменшують наслідки компрометації workflow.

Що погіршується:

- три jobs означають три запуски раннера й передачу образу артефактом; для навчального проєкту це прийнятно;
- `deploy` не має автоматичного відкату при невдалому smoke-тесті: відкат робить людина командою `kubectl rollout undo`;
- публічний репозиторій означає, що код і логи доступні всім; секретів у них немає, але це треба пам'ятати;
- складність перевіряється лише для `src/shop/api` і `src/shop/legacy`; модулі ЛР2–ЛР3 мають власні виміри й не входять у сервіс.

## Доказ, що ворота працюють

Окремий PR додавав функцію з цикломатичною складністю 12 і без тестів. `quality` падав на `make complexity`, `image` і `deploy` не запускалися; PR закрито. Виправлений PR із тією самою функцією, розбитою на допоміжні, проходить усі ворота. Посилання на червоний і зелений запуски — у розділі README «ЛР5».

## Ризики та що перевірити

- GitHub Actions може бути недоступним або вичерпати ліміт хвилин; локальний `make ci` лишається запасним шляхом.
- Trivy завантажує базу вразливостей щоразу; без мережі крок упаде. У продакшні базу кешують.
- `kind` у раннері ефемерний: після job кластер зникає, тому це демонстрація розгортання, а не середовище.
- `sed` для тегу образу — крихкий; у продакшні краще `kustomize edit set image` або окремий overlay із параметром.
- Якщо з'явиться реєстр і кілька середовищ, `deploy` треба розділити на staging/prod із ручним підтвердженням.
